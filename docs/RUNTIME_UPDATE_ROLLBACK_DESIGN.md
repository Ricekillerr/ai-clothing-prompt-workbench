# Python、Pillow 与 FFmpeg 运行时更新和回滚设计（待实施）

本文是设计，不表示现有更新器已支持更新运行时。现有 `updater.py` 按允许清单替换应用文件，以 Python 子进程执行健康检查；候选 EXE 当前固定调用 `runtime/python.exe`。运行时一旦正在使用，不能直接原地覆盖，也不能让失效的 Python 负责修复自身。本方案需要独立实现、隔离测试和发布签名基础设施；本阶段不修改现有更新器。

## 边界与版本

分别记录应用代码、Python 运行时、Pillow/FFmpeg 依赖包、数据库 schema 的版本与兼容区间。使用经过认证的启动器和独立更新助手管理四者；数据库、原始案例、图片、视频、备份、设置和密钥始终位于用户数据目录，不放入应用或运行时槽位。运行时版本采用不可变目录 `runtimes/<runtime-id>/`，每个目录包含 Python、精确锁定的 Pillow 与 imageio-ffmpeg/FFmpeg、各文件哈希、平台架构、来源、许可证清单和依赖约束。应用代码另有独立版本槽，不能混淆两类版本。运行时不带用户数据，不执行安装脚本。

正式发布清单至少列出通道、版本、操作系统与架构、最低兼容启动器/应用版本、schema 可读写范围、完整包和增量包的字节数及 SHA-256、每个文件的 SHA-256、依赖锁定版本、发布时间和迁移要求。使用可信发布密钥对清单签名，启动器内置可轮换的信任锚；SHA-256 验证完整性，签名验证来源，HTTPS 或未认证哈希不能替代签名。稳定版与测试版渠道隔离，防止回退攻击；发布密钥及 API 凭证不得进入客户端或日志。签名和密钥轮换机制必须先经安全审查。

## 安装事务

1. 检查通道、签名、版本兼容范围、磁盘容量和可恢复备份；用户正在编辑、上传、执行 AI 任务或保存时只下载不切换，安全空闲或下次启动才开始安装。
2. 下载到程序文件所在卷的独立暂存目录，支持断点续传。优先验证基于确切旧版本的增量包；基础不匹配或校验失败时放弃增量并尝试完整包。拒绝路径穿越、重复路径、链接、异常压缩比例和未列入清单的文件，解包后逐文件核对 SHA-256、大小和签名；限制目录写入范围。
3. 使用 SQLite 在线备份 API 生成一致性数据库快照，并与用户素材、关键配置建立经过验证的完整备份清单；备份保留在独立用户数据备份位置，不覆盖原件。大素材必须保持只读或采用一致性快照，备份失败阻止切换。凭据使用操作系统保护机制；日志只记事务 ID、版本、状态和脱敏错误。
4. 持久化事务记录：旧/新应用槽和运行时槽、版本与哈希、schema 状态、数据备份、预期健康检查及状态。先 fsync 日志和目录，再安装到新槽；绝不覆盖正在运行的解释器或 DLL。不可变槽写完后再次验证。
5. 使用同卷原子替换一个小型受保护的版本指针（写临时文件、刷盘、原子替换、刷目录），指针含应用和运行时共同兼容的组合与事务 ID。不能把切换多个独立指针当成原子操作。只有独立启动器/更新助手能修改指针，必须避免符号链接和目录联接越界；Windows 被占用文件、权限与异常均进入安全失败。
6. 用新槽启动受控子进程，限时验证进程仍存活、实际解释器和 FFmpeg 均来自新槽、应用及 schema 版本、数据库只读及代表性核心接口、前端资源、Pillow 解码真实小图、FFmpeg 解码真实短视频。检测失败、超时或异常必须先确认新进程及子进程已退出，记录脱敏故障，再切回旧指针。
7. 健康检查成功并验证兼容性后才将事务置为 committed，启动器打开工作台。保留至少上一可用槽、验证通过的备份和事务日志；清理应另行审计，不删除用户数据。健康检查不能作为旧数据写入或新功能正确性的全部证据。

## 数据库与回滚

应用代码更新、运行时更新、依赖更新和数据库结构迁移是独立步骤。运行时或应用版本切换不得隐式重建数据库；如需要迁移，先完成明确的兼容预检和一致性备份，再采用显式事务增量升级。旧代码不兼容高版本数据库时不得打开写入；使用现有 V1/V2 独立路径隔离旧版文件替换，并保留已验证的文件级保护。SQLite 触发器不阻止旧程序直接替换数据库，不能单独作为降级保护。

在用户写入新数据之前，如果迁移事务失败，回滚事务并校验源数据库与素材；如已切换但确认没有产生新写入，只有在校验旧版兼容且完整保留迁移后快照的情况下才可恢复备份。**一旦新 schema 已产生写入，不得用旧备份覆盖它**：保留完整新库、素材和配置，继续使用兼容 V2 的应用/运行时；若旧代码不兼容则进入只读安全恢复状态，等待兼容版本，不能自动降级数据库或丢失新单品、关系、提示词版本和 PS 记录。回滚只恢复运行时与应用指针时，必须先验证旧组合对当前 schema 的读写范围。任何无法确认写入状态、进程退出或备份完整性的情况都必须保留所有槽和数据并停止自动覆盖。

## 中断恢复状态机

事务阶段建议为 `prepared → staged → switching → checking → committed`；异常进入 `rolling_back → rolled_back`，无法安全完成则为 `recovery_required`。每一步须可重入且有已刷盘证据。启动器每次启动先检查事务；`prepared/staged` 保留旧指针并校验暂存，`switching/checking` 根据已验证指针和日志重新检查或恢复，`committed` 校验目标存在后正常启动。指针/日志不一致、签名失败、两份状态都无法证明安全或未知 schema 均进入安全恢复，不得静默删除目录。回滚后重新启动旧组合并验证应用、数据库及素材读取；失败时保留两套槽、备份和完整脱敏故障日志，给出恢复指引。

## 实施与验收门禁

先以独立测试目录验证启动器、更新助手与双槽，再接入现有应用内 UI；不得直接操作真实用户数据库。使用真实 Windows 文件锁、中文和空格路径，以及 Ubuntu 对平台无关代码运行回归。故障注入覆盖下载中断/续传、哈希与签名错误、恶意压缩包、磁盘不足、写入/原子替换失败、进程占用、Python 无法启动、Pillow/FFmpeg 缺失或损坏、健康检查超时、数据库迁移失败、每个日志状态断电重启、回滚失败、V2 写入后的降级拒绝及数据/素材完整性。必须验证自动恢复旧运行时、旧版无法覆盖活动 V2、日志脱敏和无外部依赖的离线首次启动。完成隔离 CI 后仍需全新离线 Windows VM 和实际桌面验收，才能纳入正式版本发布门禁。
