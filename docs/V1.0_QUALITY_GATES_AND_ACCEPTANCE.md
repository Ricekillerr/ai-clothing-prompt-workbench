# Prompt Atelier V1.0 — Quality Gates and Acceptance Matrix

This document is the canonical acceptance checklist for the V1.0 release. A check is complete only when its evidence is attached to a reproducible test run or a Windows acceptance report.

## Gate 0 — Source-of-truth and release integrity
- [ ] The release branch contains the exact reviewed candidate source, not a stale prototype.
- [ ] `APP_VERSION`, `installed_version.txt`, changelog, and manifest version agree.
- [ ] The updater's branch/ref, manifest URL, and raw file URL all resolve to the same release branch.
- [ ] Every manifest path exists on the release branch.
- [ ] SHA-256 values are calculated from the exact bytes served by GitHub Raw, including documented newline normalization if applicable.
- [ ] The update allowlist contains only application files; no database, references, API keys, local configuration, or user-generated files.
- [ ] The launcher and updater are compatible with the minimum supported Windows/Python setup.

## Gate 1 — Data integrity
- [ ] SQLite database is stored outside the replaceable application payload.
- [ ] Reference images are stored outside the replaceable application payload.
- [ ] Existing JSON migration is idempotent and transactional.
- [ ] A failed save leaves the previous committed data intact.
- [ ] A failed import does not partially mutate the live in-memory or persisted dataset.
- [ ] A failed delete does not remove the record from the UI before server confirmation.
- [ ] Backup contains database, references, and required local configuration without exposing credentials.
- [ ] Restore is tested against a copy and verifies record counts and image hashes.

## Gate 2 — Interaction and API correctness
- [ ] Buttons provide idle, hover, pressed, disabled, loading, success, and error feedback as appropriate.
- [ ] Long-running actions expose progress or a clear stage indicator.
- [ ] Duplicate submissions are blocked at the UI and handled safely by the API.
- [ ] API responses use truthful HTTP status codes and structured error bodies.
- [ ] The UI checks both HTTP status and response payload before reporting success.
- [ ] Search distinguishes empty results from transport, server, and parsing failures.
- [ ] Requests have timeouts and safe retry semantics.
- [ ] All existing screens and workflows pass regression tests.

## Gate 3 — Process lifecycle (Windows)
- [ ] Launch works from paths containing spaces and non-ASCII characters.
- [ ] Launch does not create duplicate service instances.
- [ ] Browser close heartbeat leads to graceful shutdown.
- [ ] A stale service is detected without terminating unrelated Python processes.
- [ ] Port conflict reports the owning PID and offers a safe recovery path.
- [ ] Restart works after normal close and after a simulated crash.
- [ ] CMD/PowerShell windows do not remain orphaned after the supported close workflow.

## Gate 4 — Updater transaction
- [ ] Manifest schema and version are validated before download.
- [ ] Each file is size-limited and hash-verified before install.
- [ ] All files are staged before any live file is replaced.
- [ ] A complete pre-update backup is made before replacement.
- [ ] Replacement is atomic per file or via a recoverable transaction.
- [ ] Any failure restores every replaced file and leaves user data untouched.
- [ ] Post-update health check verifies version endpoint and required API routes.
- [ ] Failed health check automatically rolls back.
- [ ] Successful update cleans temporary files only after verification.

## Gate 5 — Asset and case management
- [ ] Every case has stable identity and source provenance.
- [ ] Images are linked by stable paths/IDs and survive app updates.
- [ ] Batch import detects duplicates without silently overwriting.
- [ ] Delete and bulk operations support confirmation and recoverability.
- [ ] Case states distinguish verified success, pending validation, failure, and archived.
- [ ] Version history preserves previous prompt text and associated assets.

## Gate 6 — Explainable retrieval
- [ ] Hard constraints (e.g. garment category) are evaluated before soft similarity.
- [ ] Score weights are documented and configurable.
- [ ] Missing attributes are not silently treated as matches.
- [ ] Each result shows matched and mismatched attributes.
- [ ] Threshold filtering is deterministic and tested with a labelled fixture set.
- [ ] Failed/untested cases are excluded from verified-success recommendations by default.
- [ ] Retrieval quality is evaluated using precision@k/recall@k on a curated test set; an arbitrary percentage is not presented as model confidence.

## Gate 7 — Prompt composition
- [ ] Modules carry category, scope, model compatibility, language, and validation state.
- [ ] Reference-image roles and precedence are explicit.
- [ ] Conflicting constraints are detected before output.
- [ ] Composition preserves immutable user requirements.
- [ ] Output includes Chinese and English versions when requested.
- [ ] The composed prompt is traceable to its source modules and cases.
- [ ] User edits can be saved as a new version without overwriting the source.

## Gate 8 — Performance, accessibility, and maintainability
- [ ] Large asset libraries use pagination or virtualized rendering where needed.
- [ ] Search remains responsive with representative library sizes.
- [ ] Keyboard focus and visible focus indicators work throughout the app.
- [ ] Error messages are actionable and do not expose secrets or stack traces.
- [ ] Logs rotate and redact API keys and sensitive local paths.
- [ ] Dependencies are pinned or constrained and have a documented update process.
- [ ] No unused duplicate entry points or release artifacts remain in the active root.

## Release decision
V1.0 may be marked stable only when Gates 0–8 are complete, all critical/high severity issues are closed, the Windows acceptance report is attached, and backup/restore plus update/rollback have been demonstrated on a clean test copy. A passing non-Windows test suite is not a substitute for Windows acceptance.
