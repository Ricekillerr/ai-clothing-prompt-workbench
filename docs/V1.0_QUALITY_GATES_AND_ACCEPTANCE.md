# Prompt Atelier V1.0 — Quality Gates and Acceptance Matrix

This document is the canonical acceptance checklist for the V1.0 release. A check is complete only when its evidence is attached to a reproducible test run or a Windows acceptance report. The latest code-side evidence is GitHub Actions run [43388913191](https://github.com/Ricekillerr/ai-clothing-prompt-workbench/actions/runs/43388913191): 121 regression tests (120 passed, 1 Linux-only environment skip), 18 Windows Server 2025 tests passed, and all three jobs passed. This does not replace the user's own desktop/data acceptance.

## Gate 0 — Source-of-truth and release integrity
- [x] The release branch contains the isolated V0.6.5 candidate source; production `main` remains unchanged.
- [x] `APP_VERSION`, candidate branch/ref, manifest version and update source are checked by the release source/channel gate.
- [x] The updater's branch/ref, manifest URL, and raw file URL resolve to the same candidate branch.
- [x] Every manifest path exists on the release branch.
- [x] SHA-256 values are checked against the exact nine runtime files in CI.
- [x] The update allowlist contains only application/runtime/manual files; no database, references, API keys, or local configuration.
- [ ] Minimum supported Windows/Python compatibility and the user's own desktop environment are still awaiting final acceptance.

## Gate 1 — Data integrity
- [x] SQLite database is stored outside the replaceable application payload.
- [x] Reference images are stored outside the replaceable application payload.
- [x] Existing JSON migration is idempotent and transactional under regression tests.
- [x] A failed save leaves the previous committed data intact.
- [x] A failed AI import cleans copied images when the database transaction fails.
- [x] A failed delete does not remove the record from the UI before server confirmation.
- [x] Full backup contains the database and regular reference files with per-file SHA-256 verification; credentials/local configuration are not added to the update payload.
- [x] Restore is tested against isolated copies and verifies database/reference persistence and rollback behavior.
- [ ] Full backup/update/restore must still be exercised against the user's existing real database and references directory.

## Gate 2 — Interaction and API correctness
- [ ] Buttons provide idle, hover, pressed, disabled, loading, success, and error feedback as appropriate.
- [ ] Long-running actions expose progress or a clear stage indicator.
- [x] Local API validates Host, Origin, JSON Content-Type and Fetch Metadata; JSON/ZIP routes have explicit request boundaries.
- [x] API errors use structured response bodies and avoid logging request bodies/secrets.
- [x] The UI checks HTTP status and response payload before reporting save/update success on covered workflows.
- [ ] Search empty/error states and all screens still need final functional review.
- [x] Requests have bounded timeouts and safe update-start ambiguity handling.
- [ ] Full manual interaction review remains open.

## Gate 3 — Process lifecycle (Windows)
- [x] Windows Server 2025 CI exercises BAT launch, heartbeat, close, service exit and restart.
- [x] Restore cannot be interrupted by stale heartbeat shutdown; lifecycle messages remain responsive during restore.
- [ ] Launch from the user's actual paths containing spaces/non-ASCII characters.
- [ ] Duplicate-instance, stale-service, port-conflict recovery and orphaned CMD/PowerShell checks on the user's desktop.
- [ ] Restart after a real user-machine crash and long-running idle test.

## Gate 4 — Updater transaction
- [x] Manifest schema/version and all file sizes/hashes are validated before install.
- [x] All files are staged and verified before live replacement.
- [x] A complete pre-update backup is made before replacement.
- [x] Replacement uses a recoverable transaction and rollback.
- [x] Windows CI verifies user database, references and local settings survive clean install/in-place update and injected update failure.
- [x] Temporary files are cleaned only after successful verification; failed rollback preserves its recovery backup.
- [ ] Final health-check behavior and update/rollback must be rechecked on the user's existing installation.

## Gate 5 — Asset and case management
- [x] Cases have stable identity and structured source provenance.
- [x] AI approval revalidates prompt/media source paths and SHA-256 against the original scan source.
- [x] Reference images are stored outside the replaceable application payload and protected against symlink/junction redirection.
- [ ] Batch import duplicate handling, bulk delete and confirmation/recoverability need a final end-to-end review.
- [ ] Case-state transitions and version history need representative user-data validation.
- [x] Prompt revisions preserve original text and source hashes in covered workflows.

## Gate 6 — Explainable retrieval
- [x] Hard constraints such as garment category are evaluated before soft similarity in the retrieval path.
- [x] Results expose matched/mismatched attribute details in the current candidate UI.
- [ ] Score weights and missing-attribute behavior need a final documentation review.
- [ ] Threshold behavior must be tested with a curated labelled fixture set.
- [ ] Failed/untested case exclusion and precision@k/recall@k need real-library evaluation.

## Gate 7 — Prompt composition
- [x] Modules carry category/scope and model compatibility metadata in the current candidate.
- [x] Reference-image roles and precedence are explicit.
- [x] Cross-module hard conflicts are detected while garment-category scope is respected.
- [ ] Composition must be tested against immutable user requirements and real prompt fixtures.
- [x] Chinese/English output is supported when the source English text exists.
- [x] Composed prompt revisions are traceable to source modules/cases in covered workflows.
- [ ] Final usability review remains open.

## Gate 8 — Performance, accessibility, and maintainability
- [ ] Large asset libraries need representative pagination/virtualization and responsiveness measurements.
- [ ] Search performance needs measurement on a representative real library.
- [ ] Keyboard focus and visible focus indicators need a full manual pass.
- [x] Application logs avoid raw exception text, request bodies, secrets and user paths; updater logs redact install/home paths and bearer/API-key patterns.
- [x] Application and updater logs rotate at a bounded size and retain three backups.
- [ ] Dependency policy and minimum supported Python version need final documentation.
- [ ] Active root/release artifacts need a final cleanup review.

## Release decision
V1.0 may be marked stable only when Gates 0–8 are complete, all critical/high severity issues are closed, the Windows acceptance report is attached, and backup/restore plus update/rollback have been demonstrated on a clean test copy and the user's existing data. A passing non-Windows test suite or isolated Windows CI is not a substitute for the user's own Windows acceptance.
