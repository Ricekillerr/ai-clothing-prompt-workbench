## 当前真实实现

`ai_analyzer.py` 当前是一个 OpenAI 兼容分析器：

- 请求 `/chat/completions`；
- 默认 endpoint 为 `https://api.openai.com/v1`；
- 默认模型字段为 `gpt-4o-mini`；
- 支持 1–8 张图片；
- 要求 JSON object 输出；
- API Key 只用于当次请求，不保存；
- 远程端点必须 HTTPS；
- 禁止通过重定向把 API Key 转发到其他主机；
- 提示词原文和素材 SHA-256 需要保持可核验。

它不是多模型 Agent 路由器，也不是 Seedream 图片生成/编辑接口。

## 推荐的分阶段接入方案

### 阶段 A：先稳定当前单入口

保持 V0.6.5 的数据库、案例结构、原文保护、哈希校验和人工审核不变。

为后续模型配置准备：

1. 模型提供方；
2. HTTPS endpoint；
3. 实际模型 ID；
4. 输入模态与图片数量限制；
5. JSON 输出能力；
6. 超时、重试、限流和成本策略；
7. 凭据保存边界。

### 阶段 B：增加“分析适配器”，不要直接把名称写死在业务逻辑里

建议抽象：

- `AnalysisProvider`：接收提示词、图片和结构化字段要求；
- `ReviewWorkflow`：负责冲突检测、人工审核和入库；
- `ModelRunRecord`：记录提供方、模型 ID、请求时间、结果、错误和来源哈希；
- `GenerationProvider`：独立处理图片生成/编辑，不与文本分析混用。

这样可以让 DeepSeek/GLM 负责视觉分析、其他模型负责复核，而不改变 SQLite 案例结构。

### 阶段 C：多 Agent 协作必须有确定职责和人工门禁

推荐职责：

1. **视觉分析 Agent**：只描述图片证据、角色和可见属性；
2. **案例抽取 Agent**：把已确认信息整理成案例字段；
3. **疑难复核 Agent**：处理冲突、缺失和低置信度字段；
4. **提示词组装器**：只使用已审核的案例与模块；
5. **图片生成/编辑适配器**：调用独立生成接口并保存真实结果反馈。

所有 Agent 输出都不能绕过人工审核直接变成“已验证成功案例”。

## 需要用户配置时再集中提醒

真正开始模型接入时，需要用户决定或提供：

- 使用哪些真实模型提供方；
- 是否已有账号、额度和 API 权限；
- 实际可调用的模型 ID；
- API Key 的安全输入方式；
- 是否允许上传哪些图片和提示词；
- 图片生成接口的保存位置、预算和结果评估标准。

不要把截图中的展示名称直接当作已验证 API 模型 ID，也不要要求用户把密钥发到聊天正文。

## V1.0 前的模型验收要求

- 使用真实图片和提示词做小规模测试；
- 验证 JSON 字段、图片角色、原文保护和哈希；
- 比较分析结果与人工复核的一致性；
- 记录失败、超时、限流和成本；
- 验证生成结果与参考图职责是否一致；
- 不把“80% 检索门槛”解释为识别准确率或生成成功率。
