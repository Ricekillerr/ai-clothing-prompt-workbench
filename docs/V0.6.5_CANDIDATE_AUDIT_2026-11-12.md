## Blocking discrepancy
The candidate `ai_prompt_workbench.py` declares:
- `APP_VERSION = "0.6.5"`
- `GITHUB_BRANCH = "main"`

However, the candidate was intended for `release/v0.6.5-stabilization`, and the repository `main` branch is a separate older production channel. The candidate's updater builds both the manifest URL and raw file URLs from `GITHUB_BRANCH`. Therefore, changing only the branch name in documentation is insufficient; the actual candidate source and manifest must be patched together, re-hashed, synchronized to the release branch, and tested against GitHub Raw.

## Safety decision
- Do not merge the current release branch into `main`.
- Do not publish the current candidate manifest to `main`.
- Do not tell users to install this candidate yet.
- Do not delete any additional source files until the exact V0.6.5 source is synchronized and dependency scanning is repeated on that branch.
- User-local database, reference images, credentials, and settings remain untouched.

## Next technical sequence
1. Patch candidate `GITHUB_BRANCH` to the stabilization branch.
2. Recompute the candidate main-program hash in `update_manifest.json`.
3. Upload the exact reviewed runtime files to the stabilization branch as one tree update.
4. Fetch each file back from GitHub Raw and verify SHA-256 against the manifest.
5. Test manifest discovery and staged download using the actual branch URLs.
6. Only then proceed to updater install/rollback tests.
7. Windows native acceptance remains a separate mandatory gate.

This audit is a release-blocker record, not a claim that the V0.6.5 candidate has been published.
